## 1. 问题陈述

CF8 的 `ground preflight` 与 `post-takeoff` 两个阶段，目前由**同一个** `FlightReadiness`
对象驱动，且地面门消费**全部** blocking issue。其中若干 issue 依赖光学光流与近场测距，
而这两者在飞机贴地时**物理上不可用**，因此地面门要求了一个地面无法满足的条件。

结果：一台传感器完全正常的 Flow Deck Crazyflie 无法通过起飞前预检。

## 2. 真机证据（cf231，2026-09-21）

### 2.1 传感器规格约束

| 传感器 | 型号 | 有效距离 | 说明 |
|---|---|---|---|
| 光流 | PMW3901 | **80 mm – ∞** | 低于 80 mm 图像离焦，输出无效 flow |
| 下视测距 | VL53L1x | 可靠区间约 **≥ 40 mm** | < 4 cm 测距不可靠 |

来源：PX4 PMW3901 文档（"adapted to work between 80 mm and infinity"）、Bitcraze Flow deck 使用说明。

### 2.2 实测对比

`flow_drift_probe.py`，均只订阅、不发任何命令：

| 工况 | `range.zrange` | `motion.squal` | `delta_x/y` max | `xy_std` | `speed_max` |
|---|---|---|---|---|---|
| 贴地 | 0.005–0.013 m | 31.8 | 28 / 26 | 0.051 | 0.101 |
| 架高（约 0.19 m） | 0–0.348 m | 112.5 | 21 / 16 | — | — |
| 架高（0.467 m，含 7.6° 倾斜） | **0.462–0.475 m（稳定）** | **174.7** | **3 / 3** | 0.041 | 0.117 |
| 贴地（另一表面） | **0.0（恒定）** | 45.1 | 16 / 25 | 0.0096 | 0.055 |

**结论**：

1. 地面 `zrange` 的 4–13 mm 读数与 0 读数**都不是可信高度**；VL53L1x 在 < 4 cm 不可靠。
   因此 `min_startup_zrange_m` 无论取 `0.02` 还是 `0.005`，都是**用错误类型的检查**
   （近场合理性判定）去验证一个近场无法测量的量。
2. 架高后测距完全正常（0.462–0.475 m 稳定），光流质量极佳（squal 164–186，delta ≤ 3），
   证明传感器与 deck 本身**没有故障**。
3. 高度过高（0.467 m）会放大速度估计噪声（flow 测量模型 `v = flow·h/k`，`h` 越大，
   同样像素噪声映射的速度误差越大），叠加 7.6° 机体倾斜后仍会漂移 —— 这解释了
   Bitcraze "不要飞太高" 的建议，也说明**应该把稳定性判定放到起飞后的悬停高度做**。

### 2.3 当前阻塞项

```
readiness_blocking_codes = [battery_critical, pose_stability_failed, range_invalid]
```

其中 `battery_critical` 是真实阻塞（3.63 V < 3.7 V，需充电）；另两项属本文档要解决的架构问题。

## 3. 现状架构与缺陷定位

### 3.1 数据流

```
telemetry._flight_readiness()                      telemetry.py:864-981
        -> FlightReadiness{passed, issues[]}       telemetry.py:259-282
               |
               +-- protocol_server._preflight()            protocol_server.py:346-388
               |       L371-374: append 全部 blocking issue        -> GROUND gate
               |
               +-- cf8_acceptance._preflight_recheck()     cf8_acceptance.py:272-308
                       L288-290: append 全部 blocking issue        -> GROUND gate（起飞前）

cf8_acceptance 起飞后检查（与 FlightReadiness 无关，独立实现）：
        +-- _wait_for_settle() / _hover() -> _settled()        cf8_acceptance.py:504-514
        |       z 容差 + speed <= settle_velocity_mps + xy_drift <= tolerance
        +-- _inflight_health_issue()                           cf8_acceptance.py:465-502
                session / connected / pose_stream / battery / supervisor 故障 / pose 有限 / xy drift
```

### 3.2 缺陷

- `FlightReadiness` 是**单一平面**对象，没有阶段语义；地面门整体消费它。
- 起飞后**没有**基于 `range` 可靠区间、`pose_stability` 窗口、`estimator` 稳定性的
  显式 stabilization gate；`TAKING_OFF -> HOVERING` 之间只有一个较弱的 `_wait_for_settle`。

### 3.3 26 个 issue code 的分类

**A. 地面有效（与高度/光流无关）— 22 个**

| 组 | code |
|---|---|
| 能力（能力快照，非实时测量） | `xy_positioning_missing`、`z_positioning_missing` |
| 连接/新鲜度/频率 | `status_missing`、`status_stale`、`pose_missing`、`pose_stale`、`pose_rate_too_low` |
| 电池 | `battery_critical` |
| supervisor（**阶段见 §11**） | `supervisor_missing`(BOTH)、`supervisor_not_flyable`(GROUND)、`supervisor_armed`(GROUND)、`supervisor_flying`(GROUND)、`supervisor_locked`(BOTH)、`supervisor_tumbled`(BOTH)、`supervisor_crashed`(BOTH)、`supervisor_high_level_active`(GROUND)、`deck_fault`(BOTH) |
| 遥测存在性 | `velocity_unavailable`、`velocity_stale`、`range_unavailable`、`range_stale` |

## 4. 两类 gate 的职责划分（目标语义）

### 4.1 Ground launch safety gate

**目的**：确认"这架飞机现在可以安全地开始一次受监督飞行"。
**原则**：只使用**与高度和光流质量无关**的证据。

必须通过：

- 连接与遥测：`status` / `pose` 新鲜、pose 频率达标
- 能力：`xy_positioning_available`、`z_positioning_available`（来自 deck 能力快照）
- 电池：高于 critical 阈值
- supervisor：可飞、非异常 armed、未 flying、未 locked/tumbled/crashed、无 deck fault
- 遥测存在性：velocity / range / estimator variance 流均**存在且新鲜**
- estimator：variance span 稳定（滤波器层面的检查，与绝对高度无关）

**明确不包含**：`pose_stability_*`、`velocity_not_settled`、`range_invalid`。

### 4.2 Post-takeoff stabilization gate（新增，显式）

**目的**：在飞机已离地、传感器进入有效区间后，确认定位真正稳定，才允许进入 HOVER/验收判定。
**原则**：这里才是"测量质量"判定的正确位置。

**观测窗口（决策 D2，见 §9）**：本 gate 使用**独立的、以 `takeoff_target_reached`
的 monotonic 时间戳为锚点**的窗口，**不复用** `TelemetryCollector._pose_samples`
（`deque(maxlen=200)`，`telemetry.py:433`）。
原因：该 deque 连续灌入，起飞后约 20 s 内仍混有起飞前的地面样本（那时光流无效），
任何复用它的空中判定都会拿到混合有效性的数据；且 20 s 窗口无法塞进
`cf8_max_total_acceptance_time_s = 30.0`。

- 锚点：`takeoff_target_reached` 事件的 monotonic 时间戳（`cf8_acceptance.run()` 内
  `_wait_for_settle(phase="takeoff")` 返回后立即采样）
- 最短观测：锚点后**至少 `minimum_airborne_observation_s`（5.0 s）**
- 连续满足：在最短观测之上，**最近连续的 `stabilization_window_s`（3.0 s）** 全部健康
- 超时：锚点起 `stabilization_timeout_s`（10.0 s）仍未满足 → 软失败

实现类：`cf8_acceptance.AirborneStabilizationWindow`（`observe()` / `report()`），
只接收锚点之后由运行器自己轮询到的样本。

在窗口内同时满足：

- `range`：窗口内**每一个** fresh 样本都满足 `0.10 <= zrange <= 0.50`（可靠区间）
- `pose`：只用锚点后样本；`xy_span <= 0.03` 且 `xy_displacement <= 0.03`；
  沿用既有的 sample gap（`stabilization_max_sample_gap_s = 0.5`）与新鲜度约束
  （`stabilization_max_pose_age_s = 0.75`）
- **速度：严格 max 语义（决策 D4 最终形态）** —— 窗口内
  `max(|vx|) <= 0.05`、`max(|vy|) <= 0.05`、`max(|vz|) <= 0.05`、`max(speed) <= 0.08`。
  **禁止 percentile**，阈值数值不变，也不做任何"单帧豁免"。
- `estimator`：必须 fresh / converged（`estimator_variance` 存在且有限，且 airborne
  readiness 中无 `estimator_not_converged`）
- `supervisor`：airborne readiness 中无 `supervisor_cannot_fly`

**从空中门显式排除的 code**（`cf8_acceptance.STABILIZATION_READINESS_CODES` 的补集）：

| 排除项 | 原因 |
|---|---|
| `pose_stability_observation_missing` / `pose_stability_failed` | 它们来自被地面样本污染的 200 样本 deque；由本窗口用自己的锚点后样本重算 |
| `velocity_not_settled` / `range_invalid` | 由运行器自己按窗口严格 max 与 band 判定，保持单一真源 |

**硬故障 vs 软失败**：

- **硬健康故障**（`_inflight_health_issue()`）：`battery_critical`、status/pose 丢失、
  `hardware_session_changed`、`supervisor_locked` / `tumbled` / `crashed` / `deck_fault`、
  `supervisor_cannot_fly`、XY 漂移超限 —— **立即** controlled land，不等
  `stabilization_timeout_s`。
- **软收敛失败**（range / velocity / pose / estimator 未达标）：允许继续等待，
  `stabilization_timeout_s`（10.0 s）到期后 → controlled land → `FAIL`
  （`failure_code = "stabilization_timeout"`）。

**职责边界**：range 检查只回答"下视传感器数据可不可信"；"飞得够不够高"仍由既有
`z_acceptance_tolerance_m` 判定，两者不互相替代。

**失败路径**：走既有 `_abort_or_fault()` -> `_land()` -> **controlled landing**。
绝不使用 emergency stop 替代；controlled land **只发送一次**（状态机守卫）。

## 5. 设计

### 5.1 `ReadinessIssue` 增加阶段标记

```python
class ReadinessStage(StrEnum):
    GROUND = "ground"        # 仅地面门消费
    AIRBORNE = "airborne"    # 仅空中门消费
    BOTH = "both"            # 两个门都消费

@dataclass(frozen=True, slots=True)
class ReadinessIssue:
    code: str
    message: str
    blocking: bool = True
    stage: ReadinessStage = ReadinessStage.BOTH   # 默认保守：两个门都拦
```

**默认 `BOTH`** 保证未显式分类的新 issue 不会被静默放过（fail-closed）。

### 5.2 `FlightReadiness` 分区

```python
@property
def ground_issues(self) -> tuple[ReadinessIssue, ...]:
    return tuple(i for i in self.issues if i.stage in (BOTH, GROUND))

@property
def airborne_issues(self) -> tuple[ReadinessIssue, ...]:
    return tuple(i for i in self.issues if i.stage in (BOTH, AIRBORNE))

@property
def ground_passed(self) -> bool:
    return not any(i.blocking for i in self.ground_issues)

@property
def airborne_passed(self) -> bool:
    return not any(i.blocking for i in self.airborne_issues)
```

`passed` 保留原语义（全部 issue），仅在需要"全绿"展示时使用。
`to_payload()` 增加 `ground_passed` / `airborne_passed` 与每个 issue 的 `stage`。

### 5.3 地面门的 issue 归类

地面门消费 `ground_issues`。因此需把 §3.3-B 的 4 个 code 标为 `AIRBORNE`：

- `pose_stability_observation_missing` -> AIRBORNE
- `pose_stability_failed` -> AIRBORNE
- `velocity_not_settled` -> AIRBORNE
- `range_invalid` -> AIRBORNE

其余保持 `BOTH`。

### 5.4 `range` 在地面的处理

地面不再做绝对下限判定，改为：

| 条件 | code | blocking | stage |
|---|---|---|---|
| `zrange` 缺失 | `range_unavailable` | 是 | BOTH |
| `zrange` 过期 | `range_stale` | 是 | BOTH |
| `zrange` 非有限 | `range_unavailable` | 是 | BOTH |
| `zrange < range_ground_advisory_m` | `range_ground_nearfield_unreliable` | **否（advisory）** | GROUND |
| `zrange > max_reliable_zrange_m` | `range_invalid` | 是 | AIRBORNE |

**安全理由**：贴地时无法验证一个 ≥4 cm 量程的传感器；地面门只能确认"传感器存在、
在报数、数值不荒谬"。真正的距离验证放到已离地、传感器进入有效区间的
stabilization gate —— 若起飞后 `zrange` 始终不落在可靠区间，飞行以 controlled land 中止。
地面门同时仍要求 `z_positioning_available`（能力快照），两级合起来构成完整的安全论证。

### 5.5 状态机

`execution_state.py` 增加 `STABILIZING = "stabilizing"`：

```
GROUND_PREFLIGHT (ground_issues)
      -> ARMING (仅 explicit_arm_required 时)
      -> TAKING_OFF
      -> STABILIZING      <-- 新增：airborne gate
      -> HOVERING
      -> LANDING
      -> LANDED
```

`cf8_acceptance.run()` 在 `takeoff` 之后、`HOVERING` 之前插入
`await self._stabilize(origin=..., target_z_m=...)`；未通过不得进入 `HOVERING`。

### 5.6 配置项（`bridge.yaml` / `ReadinessPolicy`）

| 配置 | 默认 | 含义 |
|---|---|---|
| `range_ground_advisory_m` | `0.04` | 地面低于此值只出 advisory（VL53L1x 不可靠区） |
| `min_reliable_zrange_m` | `0.10` | 空中可靠区间下限 |
| `max_reliable_zrange_m` | `0.50`（数值不变） | 空中可靠区间上界 |

校验：`range_ground_advisory_m < min_reliable_zrange_m < max_reliable_zrange_m`。

> **命名收口（决策 D8）**：原 `max_startup_zrange_m` 已更名为 `max_reliable_zrange_m`。
> 原名把上界描述成"启动合理性上限"，而它实际界定的是**下视传感器可信区间**的上界 ——
> 这是一个空中属性。数值 `0.50` 不变。旧键按"纯改名"处理：新键缺失时**仍然生效**并给出
> `DeprecationWarning`；新旧键同时出现时**新键优先**，并再发一条明确的遮蔽警告，
> 不留下任何歧义。

空中门参数位于 `CF8AcceptancePolicy`（不在 `bridge.yaml`，属验收流程常量）：

| 参数 | 默认 |
|---|---|
| `minimum_airborne_observation_s` | `5.0` |
| `stabilization_window_s` | `3.0` |
| `stabilization_timeout_s` | `10.0` |
| `stabilization_min_zrange_m` / `stabilization_max_zrange_m` | `0.10` / `0.50` |
| `stabilization_max_abs_velocity_mps` / `stabilization_max_speed_mps` | `0.05` / `0.08` |
| `stabilization_max_xy_span_m` / `stabilization_max_xy_displacement_m` | `0.03` / `0.03` |
| `stabilization_max_sample_gap_s` / `stabilization_max_pose_age_s` | `0.5` / `0.75` |

时间预算核对：`takeoff_duration 2.5` + `settle ≈0.5` + `observation 5.0` + `hover 3.0`
+ `land 2.5` + `settle ≈0.5` ≈ **14.5 s** < `max_total_acceptance_time_s = 30.0`。

`min_startup_zrange_m` 的处理（**决策 D1**）：新增上述两个键，
`min_startup_zrange_m` **读取到即记一条 deprecation 警告并忽略**。

> **不得静默映射。** 现有部署里该键可能是本地的 `0.005`（真机联调时的暂定值）。
> 若把它当作 `min_reliable_zrange_m`，一架"空中仅离地 5 mm"的飞机会被判为**有效**
> —— 那正是本设计要推翻的错误假设。映射到 advisory 键同样会静默改变语义。
> 因此只警告、不继承，让新默认值 `0.04 / 0.10` 生效。

`minimum_airborne_observation_s` 与 `stabilization_window_s` 是两个独立条件：前者是
"离地后至少观测多久"，后者是"最近连续多久必须全绿"。二者**重叠计算**，因此最早通过时刻
为锚点 + `5.0 s`。

### 5.7 明确不改的东西（阈值不变式）

以下**全部保持不变**，本设计不通过放宽它们来"做绿"：

- `max_abs_velocity_mps = 0.05`
- `max_speed_mps = 0.08`
- `max_static_xy_displacement_m = 0.03`
- `max_static_z_displacement_m = 0.03`
- `max_sample_gap_s = 0.5`
- `minimum_observation_duration_s = 5.0`
- `max_estimator_variance_span = 0.002`
- `cf8_xy_drift_tolerance_m = 0.15`
- `link_loss_policy = controlled_land`

地面门**减少**了检查项（移走了 4 个空中项），但空中门**新增**了 range 可靠区间、
pose 窗口、estimator 三项检查。净效果是安全性更严格、定位更准确，而不是更宽松。

## 6. 兼容性与迁移

- `ReadinessIssue.stage` 默认 `BOTH`，既有构造点与测试不受影响。
- `FlightReadiness.passed` 语义不变，避免破坏既有消费者。
- `to_payload()` 只**新增**字段（`stage`、`ground_passed`、`airborne_passed`），
  Windows 侧解析按需读取，属向后兼容的增量。
- `BridgeExecutionState` 新增枚举值；`cf8_acceptance` 的事件流新增
  `stabilization_started` / `stabilization_passed` / `stabilization_failed`。
- 现有 `_wait_for_settle(phase="takeoff")` 保留，作为 STABILIZING 之前的位置检查；
  stabilization gate 是其严格超集。

## 7. 测试清单

### 7.1 地面门

1. `pose_stability_failed` + `velocity_not_settled` + `range_invalid` 存在时，
   `ground_passed is True`（不再阻塞）。
2. 同样输入下，`airborne_passed is False`。
3. `battery_critical` / `supervisor_*` / `status_stale` / `pose_stale` /
   `pose_rate_too_low` / `xy_positioning_missing` / `z_positioning_missing` /
   `range_unavailable` / `range_stale` / `estimator_not_converged`
   仍然阻塞地面门（逐项 parametrize）。
4. `zrange < range_ground_advisory_m` 时产生 `range_ground_nearfield_unreliable`
   且 `blocking is False`。
5. `zrange` 非有限 -> `range_unavailable` 阻塞（fail-closed）。
6. 未分类的新 issue（默认 `BOTH`）同时阻塞两个门。

### 7.2 空中门

7. `zrange` 在 `[min_reliable_zrange_m, max]` 内 + pose stable + velocity 达标
   -> 通过。
8. `zrange` 持续低于 `min_reliable_zrange_m` -> 阻塞。
8b. `zrange = 0.005`（旧本地值）**必须**被空中门阻塞 —— 防止旧键被静默继承（决策 D1）。
9. `pose_stability` 不稳 -> 阻塞。
10. 单轴速度或 speed 超限 -> 阻塞。
10b. 速度判定为窗口统计（决策 D4）：构造一个"单帧尖峰 `|vz|=0.06`、窗口其余样本 `|vz|<=0.01`"
    的序列，断言判定与窗口统计语义一致，并且**不会**因为单帧尖峰随机翻转。
10c. 空中 pose 窗口锚点（决策 D2）：喂入"起飞前地面样本（xy 漂移大）+ 起飞后良好样本"，
    断言离地后窗口**不包含**地面样本；若离地后样本不足 5 s，断言不给通过结论。
11. `estimator` variance span 超限 -> 阻塞。
12. supervisor tumbled / deck_fault -> 阻塞。

### 7.3 状态机与失败路径

13. 正常路径事件序：`TAKING_OFF -> stabilization_started -> stabilization_passed -> HOVERING`。
14. stabilization 失败 -> `failure_code` 明确，且 `land_calls` 恰好一次
    （controlled land），`go_to_calls == []`。
15. stabilization 失败**不得**触发 emergency stop：
    断言 `BridgeExecutionState.EMERGENCY` 未被置位。
16. `hardware_flight_enabled=false` 时 `run_cf8_acceptance` 仍返回
    `hardware_flight_disabled`，且 `arm/takeoff/land` 均未调用（回归）。
17. 缺失/非布尔 `confirm_real_flight` 仍被拒绝（回归）。

### 7.3b 配置兼容性（决策 D1）

17b. 配置含 `min_startup_zrange_m: 0.005` 时：加载成功、产生 deprecation 警告、
     且该值**不**影响 `min_reliable_zrange_m` / `range_ground_advisory_m`。
17c. 配置含 `min_startup_zrange_m` 且未提供新键时，生效值为新默认 `0.04 / 0.10`。
17d. 非法组合 `range_ground_advisory_m >= min_reliable_zrange_m` 或
     `min_reliable_zrange_m >= max_reliable_zrange_m` -> 启动即 `ValueError`（fail-closed）。

### 7.4 探针一致性（已有，扩展）

18. `flow_drift_probe._pose_report` 与 `telemetry._pose_stability` 数值一致
    （已实现，见 `tests/integration/test_flow_drift_probe.py`）。
19. 新增：探针的 `airborne` 判定与空中门 policy 一致。

### 7.5 真机（非飞行）

    同时 `pose_stability_failed` / `range_invalid` 仅出现在 airborne 集合中。
21. 架高 12–15 cm 静止实测：`zrange` 落在可靠区间、`squal` 显著上升，

## 11. Step 2.5 — supervisor 阶段审计

### 11.1 为什么必须做

第 1 步把 supervisor 相关的 9 个 code 全部留在 `BOTH`（默认值），这是**阶段语义错误**：
`supervisor_not_flyable` 的判定条件是
`not (can_be_armed or (auto_arm and armed)) or not can_fly` —— 这是"**能否从这里起飞**"
（handover / arming-ready）的语义。一架**已经在飞**的飞机，在手动 explicit-arm 模式下
报告 `armed=True`、`auto_arm=False`、`can_be_armed=False`、`flying=True`；
若空中门复用这条判定，**每一次正常飞行都会被判为失败**。

### 11.2 最终分类

| 阶段 | code | 判据 |
|---|---|---|
| **GROUND** | `supervisor_not_flyable` | `not arming_ready or not can_fly`（handover 语义） |
| **GROUND** | `supervisor_armed` | `armed and not auto_arm` |
| **GROUND** | `supervisor_flying` | `flying`（起飞前不应已在飞） |
| **GROUND** | `supervisor_high_level_active` | `high_level_control_active`（起飞前不应已接管） |
| **AIRBORNE** | `supervisor_cannot_fly`（**新增**） | `not can_fly` |
| **BOTH** | `supervisor_missing` | supervisor 遥测缺失（`status is None`） |
| **BOTH** | `supervisor_locked` | 车辆终态 |
| **BOTH** | `supervisor_tumbled` | 车辆终态 |
| **BOTH** | `supervisor_crashed` | 车辆终态 |
| **BOTH** | `deck_fault` | 硬件故障 |

要点：

1. `supervisor_not_flyable` **不再**承担"飞行中 `can_fly=false`"的职责；该职责由
   `supervisor_cannot_fly`(AIRBORNE) 承担，语义明确、不依赖 arming-ready。
2. `supervisor_not_flyable` 的**条件本身不变**（仍含 `not can_fly`），因此 `can_fly=false`
   在地面仍被阻塞 —— 只是**经 GROUND code** 阻塞，空中经 AIRBORNE code 阻塞，

3. CF8 的 `_inflight_health_issue()` 同时**直接 fail-closed**：`supervisor.can_fly is False`
   → 立即抛 `supervisor_cannot_fly` → 硬故障路径 controlled land（不等 stabilization timeout）。

## 12. Step 3.5 — capability snapshot 改为 session-scoped freshness

### 12.1 真实 bug

`capability_snapshot_max_age_s`（默认 3600 s）原先在**每次** `capabilities()` /
`telemetry_payload()` 轮询时重新判定。于是：

1. session 建立时 snapshot 新鲜 → `positioning_mode = flow`，一切正常；
2. wall-clock 走过 1 小时，snapshot 文件过期；
3. 只要 ROS deck parameter 读取出现一次失败（服务暂时不可用、参数未 set、
   读取超时……），就会回落到 snapshot，而此时 snapshot 已 stale；
4. **同一个活着的 session 中途** capability 被撤销 → `positioning_mode = unknown`
   → readiness 出现 `xy_positioning_missing` / `z_positioning_missing`，
   尽管 Flow2 / ZRanger2 完全正常。

即：TTL 被当成了"反复体检"，而它实际应该是"建立信任时的一次性判据"。

### 12.2 目标语义（实现契约）

| # | 语义 |
|---|---|
| 1 | capability snapshot 新鲜度**只在授予判决的那一刻**判定 |
| 2 | 授予顺序：live ROS deck params 可用 → 用 live；否则 fresh snapshot 可用 → 接受 snapshot；两者都不可用 → fail closed（`positioning_mode = unknown`） |
| 3 | 一旦当前 `session_id` 已确认并授予判决：`Flow2` / `ZRanger2` / `positioning_mode` **在本 session 生命周期内固定**，不再重读 |
| 4 | wall-clock 后续超过 snapshot TTL **不得**在同一 session 中途撤销能力 |
| 5 | `disconnect` / hardware session changed / reconnect：session capability 失效，新 session **重新执行**完整判定 |
| 6 | Bridge **不得**在 Crazyswarm2 占用 Crazyradio 时自动启动 firmware probe |
| 7 | Bridge **不得**自动停止/重启 Crazyswarm2 来刷新 snapshot |
| 8 | snapshot 在**新 session 开始前**就已 stale 时仍必须 fail closed |

### 12.3 实现

`Crazyswarm2Adapter` 中：

- `_session_id`：唯一由 `_sync_session_from_snapshot()` 维护；`connected` 为真且当前无
  session → 新建 uuid；`connected` 为假 → 置 `None`。
- `_capability_pin_session_id`：**已授予判决所属的 session**。`None` 表示本 session 还没有
  被授予判决（即 unknown，非权威）。
- `_capability_source` / `_capability_captured_at` / `_capability_diagnostics`：已授予判决的元数据。
- `_clear_session_capability(diagnostic)`：新建 session / session 失效 / `disconnect()` 时调用，
  丢弃判决并把 positioning 复位为 `UNKNOWN_POSITIONING`。
- `_grant_session_capability(capabilities, source, captured_at)`：**每 session 只写一次**，
  记录 `_capability_pin_session_id = _session_id`。
- `_withhold_session_capability(diagnostics)`：报告 unknown（fail closed）但**不**打上
  `_capability_pin_session_id`，因此本 session 仍可在后续调用中重新尝试。
- `_refresh_positioning_capabilities()`：
  1. sync session；
  2. 无 session → `_clear_session_capability(...)` → unknown，**不再回落到 snapshot**；
  3. `_capability_pin_session_id == _session_id` → **直接返回**（不重读、不降级、不看 TTL）；
  4. 否则按 §12.2-2 的顺序尝试授予（读取间隔由 `_capability_read_interval_s` 限流）。

`_fallback_to_snapshot(diagnostic)` 是唯一的 snapshot 入口，每次都用**当下**的 wall clock
判定 `load_capability_snapshot(..., max_age_s=capability_snapshot_max_age_s)`。

### 12.4 为什么"授予后固定"而不是"每 session 封死（含 unknown）"

被修复的故障是**撤销**。把"未授予"状态也封死会让一次瞬时参数服务抖动把整个 session
钉死在 unknown，直到重新建立 session —— 既没有安全收益（unknown 本身就是 fail closed），
又制造了一个不必要的可用性悬崖。因此采用**写一次授予**语义：

- 判决一旦授予 → 本 session 内绝对不变（满足 §12.2-3/4）；
- 尚未授予 → 继续报告 unknown（满足 §12.2-2 的 fail closed），并按限流重试；
- 因为 snapshot 的 age 只会增长，**已经 stale 的 snapshot 永远无法在后续被接受**
  （满足 §12.2-8），而 live ROS 参数随时可用于授予（首选来源，永远是最新的证据）。

跨 session 不泄漏：`_capability_pin_session_id` 与 `_session_id` 绑定，session 变更时
先 `_clear_session_capability()`，新 session 必须重新走完 §12.2-2。

### 12.5 §12.2-6/7 的实现方式

Bridge 侧根本不存在这条路径：`crazyswarm_adapter.py` 不 import `subprocess` / `os.system` /
`Popen`，不 import `cflib`，不调用 `probe_cflib_capabilities`，也没有任何
`ros2 launch` / `pkill` 之类的进程控制。capability snapshot 只有独立 CLI
（`python -m dmp_crazyflie_bridge.capability_probe`）在**操作员手动**、且 Crazyswarm2 已停止时
才会写入。回归测试同时做两件事：

- 行为断言：在"参数服务不可用 + snapshot 已 stale + 反复调用"的场景下，
  monkeypatch 的 `probe_cflib_capabilities` **一次都没有被调用**；
- 源码扫描：`crazyswarm_adapter.py` 中不出现 `probe_cflib_capabilities` / `SyncCrazyflie` /
  `crtp` / `subprocess` / `Popen` / `os.system` / `pkill` / `ros2 launch`。
