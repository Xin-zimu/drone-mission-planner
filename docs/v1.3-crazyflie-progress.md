# v1.3 Crazyflie Execution Progress

## CF8.1 Ground/Airborne Readiness Split (steps 1–3)

### Summary

Ground launch preflight no longer demands evidence that only exists once the vehicle is
airborne. Readiness issues now carry a stage, the ground gates consume only
altitude/flow-independent issues, and the down-range band is expressed with two keys that
match what the sensor can actually measure. No flight threshold was loosened and no flight
path was touched.

### Readiness stages

`ReadinessIssue` gained `stage: ReadinessStage` (`ground` / `airborne` / `both`), defaulting
to `both` so a newly added, unclassified issue is never silently dropped by either gate.
`FlightReadiness` gained `ground_issues`, `airborne_issues`, `ground_passed` and
`airborne_passed`. `passed` keeps its previous meaning (no blocking issue at all) and
`to_payload()` adds `ground_passed`, `airborne_passed` and a per-issue `stage`.

Four issue codes are now `airborne`, because they depend on measurements that are invalid
on the ground:

- `pose_stability_observation_missing`, `pose_stability_failed` — need valid optical flow
  (PMW3901: 80 mm to infinity).
- `velocity_not_settled` — same dependency.
- `range_invalid` — the VL53L1x is unreliable below roughly 4 cm.

The other 22 codes stay `both`.

### Down-range band

| Config | Default | Meaning |
|---|---|---|
| `range_ground_advisory_m` | `0.04` | below this on the ground -> non-blocking `range_ground_nearfield_unreliable` (`stage=ground`) |
| `min_reliable_zrange_m` | `0.10` | airborne reliable band floor |
| `max_reliable_zrange_m` | `0.50` | airborne reliable band ceiling (renamed from `max_startup_zrange_m`, value unchanged) |

`zrange > max_reliable_zrange_m` or `zrange < min_reliable_zrange_m` raises the airborne-only
blocking `range_invalid`. A non-finite reading raises blocking `range_unavailable` on **both**
gates (fail-closed). Configuration must satisfy
`range_ground_advisory_m < min_reliable_zrange_m < max_reliable_zrange_m`, otherwise
construction raises `ValueError`.

`min_startup_zrange_m` is deprecated: it is still parsed, emits a `DeprecationWarning`, and
is **ignored**. It is deliberately not mapped onto either new key — the retired value was
often lowered to a few millimetres to force a ground reading through, and reusing it as the
airborne floor would declare a vehicle that never left the ground to be valid.

`max_startup_zrange_m` was renamed to `max_reliable_zrange_m` (the value bounds where the
down-range sensor is *reliable*, an airborne property, not a startup plausibility bound). It
is a pure rename, so the legacy value is still honoured when the new key is absent; the old
key emits its own `DeprecationWarning`, and when both keys are present the new key wins
outright and a second warning names the shadowed key. No ambiguity is left to the loader.

### Gate behaviour

`protocol_server._preflight()` and `cf8_acceptance._preflight_recheck()` now skip issues
whose `stage` is `airborne`, so they consume the `ground`/`both` set. Legacy readiness
payloads without a `stage` are treated as `both` and therefore keep blocking — no silent
bypass. `_append_unique_issue()` previously rebuilt its dict with only `code` / `message` /
`blocking`; it now also preserves `stage`, otherwise the field would have been dropped from
`run_preflight` reports.

## CF8.1 Ground/Airborne Readiness Split (steps 1–3)

### Step 2.5 — supervisor stage audit

Step 1 left all nine supervisor/deck codes on the default `both` stage, which is a stage
semantics error: `supervisor_not_flyable` is an *arming-ready / handover* test
(`not (can_be_armed or (auto_arm and armed)) or not can_fly`). A vehicle that is already
flying under manual explicit-arm reports `armed=True`, `auto_arm=False`,
`can_be_armed=False`, `flying=True`, so re-using that check airborne would fault every
normal flight.

The audited classification, exported as constants in `telemetry.py`:

| stage | codes |
|---|---|
| `ground` | `supervisor_not_flyable`, `supervisor_armed`, `supervisor_flying`, `supervisor_high_level_active` |
| `airborne` | `supervisor_cannot_fly` (**new**) |
| `both` | `supervisor_missing`, `supervisor_locked`, `supervisor_tumbled`, `supervisor_crashed`, `deck_fault` |

`supervisor_not_flyable` keeps its condition (still includes `not can_fly`) so a ground
`can_fly=False` is still blocked, now via a ground code; the airborne case is carried by the
new, explicitly named `supervisor_cannot_fly`. CF8 additionally fail-closes in
`_inflight_health_issue()`: `supervisor.can_fly is False` raises `supervisor_cannot_fly`
immediately and goes straight to the controlled landing path.

Regression coverage sweeps all `2**12` raw supervisor bit patterns and asserts every emitted
code's stage equals the declared one, and that the sweep covers the declared set exactly.

### Step 3 — post-takeoff `STABILIZING` gate

`BridgeExecutionState.STABILIZING` was added and `cf8_acceptance.run()` now follows
`taking_off -> stabilizing -> hovering -> landing`. `AirborneStabilizationWindow` holds the
gate's evidence: it is anchored on the monotonic timestamp of `takeoff_target_reached` and
only ever sees samples the runner polls after that anchor, so it never touches
`TelemetryCollector._pose_samples` (200 samples ≈ 20 s at 10 Hz, still full of pre-takeoff
ground samples right after liftoff).

Gate parameters (production defaults): `minimum_airborne_observation_s = 5.0`,
`stabilization_window_s = 3.0`, `stabilization_timeout_s = 10.0`. Inside the most recent
continuous 3 s window every fresh sample must satisfy `0.10 <= range.zrange <= 0.50`;
velocity uses **strict max semantics** — `max(|vx|) <= 0.05`, `max(|vy|) <= 0.05`,
`max(|vz|) <= 0.05`, `max(speed) <= 0.08`, no percentile and no single-sample exemption;
pose uses anchor-post samples only with `xy_span <= 0.03` and `xy_displacement <= 0.03`
plus the existing sample-gap and freshness constraints; the estimator must stay fresh and
converged.

Hard health faults (battery critical, lost status/pose, changed hardware session,
locked/tumbled/crashed/deck fault, revoked `can_fly`, XY drift) go to the controlled
landing path immediately; soft convergence shortfalls wait for `stabilization_timeout_s`
and then fail as `stabilization_timeout` through the same controlled landing, which is sent
exactly once and never replaced by emergency stop.

`pose_stability_*`, `velocity_not_settled` and `range_invalid` stay out of
`STABILIZATION_READINESS_CODES`: the first two come from the ground-contaminated collector
deque, and the last two are recomputed by the runner from its own anchored window, keeping a
single source of truth.

### Step 3.5 — session-scoped capability freshness and band-ceiling rename

`capability_snapshot_max_age_s` used to be re-evaluated on every telemetry poll, so an hour
into a live session the cflib snapshot aged out and the next transient parameter-read failure
silently withdrew XY/Z positioning (`positioning_mode = unknown`) from a healthy Flow2 +
ZRanger2 vehicle, leaving readiness blocked on `xy_positioning_missing` /
`z_positioning_missing`.

Freshness is now judged **once per hardware telemetry session**, at the moment a verdict is
granted, and the granted verdict is then pinned for the rest of that session:

- a new session starts with no capability at all (`_session_id` transition clears the pin);
- live `crazyflie_server` deck parameters win; otherwise a snapshot that is fresh *at that
  moment* is accepted; otherwise the adapter fails closed (unknown) and keeps retrying,
  rate limited, until a source grants a verdict;
- `_capability_pin_session_id` binds the granted verdict to its session, so
  `_refresh_positioning_capabilities()` returns immediately for a pinned session — no
  re-read, no downgrade, and no wall-clock TTL re-check;
- `disconnect()`, a stale status stream, or a changed session id clears the pin and the next
  session re-runs the whole decision from scratch, so capability never leaks across sessions;
- a snapshot that was already stale before the session started stays rejected, because its
  age only grows.

The adapter never starts a firmware probe and never stops or restarts Crazyswarm2: it has no
`subprocess` / `Popen` / `os.system` / `cflib` / `SyncCrazyflie` path at all, and a regression
test asserts both the behaviour (a monkeypatched `probe_cflib_capabilities` is never called
during an unresolved, already-stale session) and the source text.

### Step 3.6 — estimator convergence now reads Kalman **velocity** covariance

`estimator_not_converged` was judged from `kalman.varX/varY/varZ`, which are the Kalman
**position** covariance. With flow-only positioning that quantity grows to the firmware
`MAX_COVARIANCE` ceiling and then sits there with a span of exactly zero, so the span-based
policy degenerated into "always converged".

Live evidence on `cf231` (stationary, 13 cm stand, 30 s, both topics sampled together):

| variable | min | max | span | mean |
|---|---|---|---|---|
| `kalman.varX` (position) | 99.9995 | 99.9995 | **0** | 99.9995 |
| `kalman.varY` (position) | 99.9995 | 99.9995 | **0** | 99.9995 |
| `kalman.varPX` (velocity) | 1.144523e-4 | 2.398826e-4 | **1.254303e-4** | 1.525309e-4 |
| `kalman.varPY` (velocity) | 1.150180e-4 | 2.423401e-4 | **1.273221e-4** | 1.535344e-4 |
| `kalman.varPZ` (velocity) | 1.688753e-4 | 2.317207e-4 | **6.284539e-5** | 1.989496e-4 |

The official cflib `wait_for_position_estimator()` gates on `varPX/varPY/varPZ`; the DMP
policy now does the same.

Changes:

- `dmp_readiness` in the Crazyswarm2 `crazyflies.yaml` now logs
  `range.zrange, kalman.varPX, kalman.varPY, kalman.varPZ`. The block is still **14 bytes**
  (uint16 + three float32) and is still parsed positionally.
- `telemetry.py` renames every constant, field, index and message to velocity-covariance
  semantics: `DMP_READINESS_VAR_PX/PY/PZ_INDEX`, `EstimatorVarianceTelemetry.var_px/py/pz`,
  `DmpReadinessLogSample.var_px/py/pz`, `record_estimator_variance(var_px, var_py, var_pz)`.
- New explicit wire contract so nobody silently reads velocity covariance as position
  covariance: the payload emits
  `{"kind": "velocity_covariance", "source": "kalman.varPX/PY/PZ", "variables": [...],
  "var_px", "var_py", "var_pz"}` and no longer emits `var_x`/`var_y`/`var_z`.
  `cf8_acceptance` requires `kind == "velocity_covariance"` plus finite `var_p*` and fails
  closed otherwise.
- **Saturation fail-closed** (new, the only behavioural addition): a covariance at or above
  `estimator_max_covariance * estimator_saturation_fraction` (defaults `100.0 * 0.5 = 50.0`)
  is refused *however stable it looks*, and this is evaluated **before** the span test
  because a saturated value has span 0. The guard is deliberately loose — healthy velocity
  covariance is five orders of magnitude below it — so it only catches the degenerate
  "stably saturated = falsely converged" case.
- `max_estimator_variance_span` was **not** retuned (still `0.002`); the healthy measured
  span is 1.25e-4, leaving ~16x headroom.

Tests added: small stable `varP` passes; `varP` span > policy fails; saturated `varP` with
span 0 fails (including exactly at the guard and just below it); stale / NaN / Inf fail
closed; healthy `varP` plus healthy pose/velocity/range leaves both gates passing.

## CF8.1 Hardware Bring-up (cf231)

### Summary

First real-hardware bring-up of the CF8.1 path against `cf231` (Flow deck v2 + Z-ranger v2;
no Lighthouse, Loco or DWM1000). Two code defects were found and fixed, one operational
trap was found and given regression coverage, and the ground readiness architecture was
shown to demand sensor measurements that are physically unavailable while the vehicle
rests on the ground. No flight command was sent at any point.

### Fixed: supervisor auto-arm false positives

Firmware reports `supervisor_info_raw = 526` (`armed | auto_arm | can_fly |
high_level_trajectory_finished`) with `can_be_armed = 0` while parked and waiting for a
takeoff command. The previous logic required `can_be_armed` and treated `armed` as a
fault, so a healthy auto-arm vehicle produced both `supervisor_not_flyable` and
`supervisor_armed`.

`SupervisorInfo` now exposes `arming_ready` (`can_be_armed or (auto_arm and armed)`) and
`unexpectedly_armed` (`armed and not auto_arm`) as the single source of truth, shared by
`_supervisor_issues()` and `safe_for_preflight`. Explicit-arm builds keep the strict
semantics: armed without auto-arm remains a blocking fault and `safe_for_preflight` is
False. Confirmed on hardware — both false positives are gone and `safe_for_preflight`
is True.

### Fixed: `safe_for_preflight` disagreed with the readiness gate

`SupervisorInfo.safe_for_preflight` still used the pre-auto-arm expression, so telemetry
payloads could report `safe_for_preflight=false` while readiness passed. It is now derived
from the same two properties as the gate. A repo-wide audit confirmed it has no other
consumer (it is serialized only).

### Fixed: capability snapshot expiry silently withdrew positioning

`capability_snapshot_max_age_s` defaults to 3600 s. When the cflib snapshot expired
mid-session the adapter could no longer read the deck parameters, reported
`positioning_mode=unknown`, and readiness began blocking on `xy_positioning_missing` /
`z_positioning_missing` — even though both decks were physically present and healthy.
Refreshing requires exclusive radio access (stop Crazyswarm2, re-run the capability probe,
restart), because cflib and the C++ backend cannot share the Crazyradio. Adapter-level
regression coverage was added.

### Found (design change proposed, not implemented): ground readiness demands airborne signals

`FlightReadiness` is a single flat object consumed wholesale by the two ground gates
(`protocol_server._preflight()` and `cf8_acceptance._preflight_recheck()`), while the
post-takeoff checks are a separate, weaker implementation. Of the 26 readiness issue
codes, four depend on measurements that are invalid on the ground:

- `pose_stability_observation_missing`, `pose_stability_failed` — need valid optical flow;
  the PMW3901 is specified for 80 mm to infinity.
- `velocity_not_settled` — same dependency.
- `range_invalid` — the VL53L1x is unreliable below roughly 4 cm, so the observed 4–13 mm
  ground readings and the 0 mm readings are both untrustworthy heights. `min_startup_zrange_m`
  therefore applies a near-field plausibility check to a quantity the sensor cannot measure
  near-field; neither `0.02` nor `0.005` is a defensible basis.

Measurement evidence at three heights, drone static (see `flow_drift_probe.py`):

| Condition | `range.zrange` | `motion.squal` | `deltaX/Y` max | `speed_max` | `xy_std` |
|---|---|---|---|---|---|
| resting on floor | 0.005–0.013 m | 31.8 | 28 / 26 | 0.101 | 0.051 |
| ~0.233 m, 5.5° tilt | 0.228–0.236 m | 98.3 | 5 / 5 | 0.027 | 0.015 |
| ~0.467 m, 7.6° tilt | 0.462–0.475 m | 174.7 | 3 / 3 | 0.117 | 0.041 |
| ~0.167 m, 2.3° tilt | 0.161–0.173 m | 87.6 | 6 / 9 | 0.062 | 0.014 |

Range and flow quality are healthy at height, which confirms the decks are not faulty.
Velocity noise scales with height because the flow measurement model is `v = flow·h/k`;
at 0.467 m the noise is roughly 3× that at 0.15 m, which is why raising the vehicle is not
by itself a fix. Reducing height and levelling improved `vx_abs_max` from 0.108 to 0.012
and removed `velocity_not_settled`.

The proposed ground/airborne split — a `ReadinessStage` tag on each issue, a ground gate
restricted to height-independent evidence, a non-blocking advisory for sub-4 cm ground
range, and a new explicit `STABILIZING` gate after takeoff that validates range inside its
reliable band plus pose/velocity/estimator stability — is specified in
`docs/v1.3-cf81-ground-airborne-readiness-split.md`. No threshold is loosened by that
design; the ground gate drops four checks and the airborne gate adds three.

### Tooling added

## CF8.1 Hover Settle Hardening

### Summary and root cause

The former hover loop stopped once its minimum duration elapsed and
`settled_since` was non-null. It never compared the elapsed stable time with
`settle_duration_s`, so one settled sample could incorrectly finish hover.

Hover now requires **minimum hover duration + continuous settle window** at the
current sample. An unstable sample clears the window; stable intervals are never
added together. The minimum and settle durations remain independent parameters.
The acceptance start time anchors the existing total deadline, checked before
success (including equality). Expiry during hover yields `hover_settle_timeout`
and enters the existing controlled landing path. The final poll sleep is capped
at the remaining deadline.

### Timing/state review

- `_wait_for_settle()` and `_land()` already require continuous telemetry-based
  completion with bounded phase deadlines. Replaced truthiness initialization of
  `settled_since` with an explicit `None` check to preserve a valid zero timestamp.
- `_abort_or_fault()` retains controlled landing and preserves the initiating
  failure code. Cleanup landing retains its own bounded landing timeout after
  hover's total deadline expires; a hover timeout cannot become a PASS.
- Service acknowledgement remains distinct from physical completion. No full
  static preflight was added to controlled landing; no flight unlock changed.

## CF8 Supervised Takeoff-Hover-Land Acceptance

Software implementation PASS; CF8 live flight NOT RUN.

### Source findings

- Crazyswarm2 defines single-robot `/cf/takeoff`, `/cf/land` and `/cf/arm`
  services as `crazyflie_interfaces/srv/Takeoff`, `Land` and `Arm`.
- Crazyswarm2 service callbacks call `cf_.takeoff(...)`, `cf_.land(...)` or
  `cf_.sendArmingRequest(...)` and then return. The service response is command
  dispatch acknowledgement, not physical completion.
- `cflib.crazyflie.high_level_commander.HighLevelCommander.takeoff()` and
  `.land()` document their height argument as absolute meters. CF8 therefore
  captures `origin_z` and uses `target_z = origin_z + takeoff_delta_m`, then
  lands to `origin_z`.
- Crazyswarm2 `hello_world.py` and other examples use takeoff/land without an
  explicit arm call, while `arming.py` demonstrates the independent arming
  service. DMP defaults `cf8_explicit_arm_required=false` and supports enabling
  explicit arm/disarm by local policy if a supervised setup requires it.
- Firmware supervisor state exposes can-be-armed, armed, can-fly, flying,
  tumbled, locked, crashed, HLC state and deck fault bits. CF8 in-flight health
  uses dynamic checks and does not reuse static preflight velocity/stability
  gates during ascent or landing.

### Architecture

- Added `HardwareFlightAcceptanceRunner`, a dedicated CF8 runner. It does not
  call `MissionExecutor.execute()` and therefore cannot open XY `go_to`, route
  execution, trajectory upload, return-to-home or multi-waypoint mission paths.
- Hardware `execute_mission` remains `execution_not_implemented`.

### CF8 state machine

```text
preflight_recheck
-> arming (only if cf8_explicit_arm_required=true)
-> taking_off
-> hovering
-> landing
-> landed
```

Faults during ascent/hover enter controlled landing when possible. Ordinary
tracking, battery, pose/status loss, supervisor unsafe or session-change faults
do not trigger emergency motor stop automatically.

### Completion criteria

- Takeoff completion is telemetry-based: fresh status/pose, unchanged session,
  safe supervisor, battery not critical, finite pose, bounded XY drift,
  `abs(z-target_z)` inside tolerance and low speed for the settle window.
- Hover must maintain bounded Z error, XY drift, low speed, telemetry freshness,
  safe supervisor and battery over the configured duration/settle window.
- Landing completion is telemetry-based: near `origin_z`, low speed, fresh
  telemetry and supervisor no longer reporting flying. If DMP explicitly armed,
  disarm is requested only after landing is confirmed.
