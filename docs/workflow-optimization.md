# 流程优化总结（DSH 闭环协议）

> 对象：本仓库推进过程中使用的 DSH「合同 → 声明 → 实现 → 对账 → 归零」流程。
> 数据来源：本会话实跑与摩擦账本 `d67ee481.friction.jsonl`。

## 1. 问题诊断（实测）

| 症状 | 实测数据 | 性质 |
|---|---|---|
| 被拒次数多 | 17 个执行动作、**14 次工具被拒**（write-gate×8、converge×5、declare×1） | 一半以上可避免 |
| 每轮面板长 | 每次 declare/converge 返回完整断言清单与诊断，约 1.5～2.5k token | 协议固定成本 |
| 合同重发 | 11 条断言全文，被拒一次就要重发 | 判别力闸/组判据闸各逼我重发过 |
| 低信息量预测 | 预测「自己写了几个测试」（6 vs 实际 7）→ 回炉 | 预测对象错 |
| 重复验证 | 同一件事既写探针又写测试；全量 pytest 跑 20+ 次 | 可合并 |

## 2. 已实施规则（本轮起生效）

1. **写文件前先 `optimal_declare`**：write-gate 的 8 次拒绝全部是顺序错误。
2. **预测只打系统行为数字**：状态枚举数、方向性（A→B vs B→A）、降级状态、数值偏差；**不预测自己写了几个测试/文件**。
3. **静态检查批量化**：一次 `ruff check --fix` + 一次 `mypy` 收全错误再改，不「改一个跑一次」。
4. **过程中只跑定向测试**，全量 pytest 只在收尾跑一次。
5. **探针与测试不重复**：能被 pytest 证明的就不再写探针；探针只用于给 converge 提供 ≥2 独立通道的台账证据。
6. **合同断言压到 4～6 条**，每条覆盖一个可测面。
7. **激进档**：一个阶段一个动作，只在阶段末验证。

## 3. 实测效果

| 轮次 | 模式 | 动作数 | 主观耗时 |
|---|---|---:|---|
| F2-b（时间线/账本/报告/甘特） | 每组一步 | 6 | 约 21 分钟 |
| F3-a（接口+代价矩阵+VRPTW+13 测试） | **激进档：1 动作** | **1** | **约 4 分钟** |

结论：**激进档对「一次能想清楚的阶段」收益最大**；代价是单步失败时回滚更贵，因此阶段范围必须切得干净（F3-a 只做 OPT-01～03）。

## 4. 仍存在的浪费与待改项

| 浪费 | 原因 | 改法 |
|---|---|---|
| 文档+提交被迫另开一单 | 合同归零后 write-gate 关闭写入 | **把文档与提交并入阶段动作本身** |
| `vExpect` 写错被拒（本会话 2 次） | 新合同会把档位重置为 `far`，写 `maintain` 非法 | **一律省略 `vExpect`**，让引擎按档位推导 |
| 组判据被记为红导致组落账被拒 | decompose 的 `cmd:` 指向尚不存在的测试文件 | **组判据只指向已存在的绿文件**；新文件的验证放断言 measure |
| 独立复核子代理未返回 | 一次给了 8 条主张 + 对抗式探索，范围过大 | 复核任务**限制为 1～2 条主张 + 明确时限** |

## 5. 一句话总结

省流的关键不是「少做验证」，而是**少重发、少回炉、少重复**：
预测打系统数字、写前先声明、检查批量化、文档并入动作、合同压到 4～6 条。
